OVERVIEW
--------
This SOP covers keyword files dropped into s3://test-0v1-ioonh/error/. Each
file names one member via a pMEME_HEALTH_ID field. Before that member's
data may proceed to input/ for downstream processing, the member must be
validated against BOTH the eam and facets Postgres tables.

pMEME_HEALTH_ID corresponds to:
  - eam.member_id
  - facets.mem_health_id
(same identifier, two column names - see sql/create_eam_facets_tables.sql)

MATCH RULE — READ THIS CAREFULLY
---------------------------------
Each kwd file holds one or more comma-separated @FIELD="VALUE" records per
line (e.g. RECTYPE="MEMD" detail lines mixed with RECTYPE="MEME" member
lines, matching a real extract like:
    @RECTYPE="MEME",@pMEMD_UPDATE_CD="AP",@pMEME_REL="M",@pMEME_HEALTH_ID="M1001"
). Only RECTYPE="MEME" lines carry @pMEME_HEALTH_ID - a single file may
reference multiple members; process every one found.

For every file in s3://test-0v1-ioonh/error/:
  1. Extract every @pMEME_HEALTH_ID="<value>" occurrence from the file.
  2. For each one, look up eam.member_id = pMEME_HEALTH_ID.
  3. Look up facets.mem_health_id = pMEME_HEALTH_ID.
  4. If either lookup finds no row -> INELIGIBLE, print console message,
     skip this member.
  5. If both rows exist, check EACH row independently for:
       has_active = true
       planname in ('MA', 'MAPD')
       confirmation_letter_went = true
       member_exist_in_eam = true
       welcome_kit_triggered = true
       id_card_triggered = true
       pcp_letter_went = true
       effective_date <= today <= term_date (not yet termed)
  6. If ANY of these checks fails on EITHER row -> INELIGIBLE, print a
     console message naming exactly which check(s) failed, skip this
     member.
  7. If ALL checks pass on BOTH rows -> ELIGIBLE. Take the HIC value from
     the facets row.

STEP 1 — LOOK UP THE MEMBER IN BOTH TABLES
--------------------------------------------
  A) No matching row in eam, or no matching row in facets
     Action  : flag_member_ineligible
     Approval: AUTO
     Why     : Member record does not exist in one or both source tables.

  B) Matching row exists in BOTH eam and facets
     Action  : validate_eligibility (proceed to Step 2)
     Approval: AUTO

STEP 2 — VALIDATE ELIGIBILITY FLAGS AND DATE VALIDITY
--------------------------------------------------------
  A) Any check fails on the eam row OR the facets row
     Action  : flag_member_ineligible
     Approval: AUTO
     Why     : Console message lists exactly which check(s) failed on
               which table(s); member is not exported.

  B) All checks pass on BOTH the eam row AND the facets row
     Action  : export_eligible_member_hic
     Approval: AUTO
     Why     : Member is fully eligible - export the HIC from the facets
               row.

OUTPUT
------
EACH source kwd file in error/ gets its OWN output object in input/, named:
    EAF_<YYYYMMDD_HHMMSS>.txt
(current date and time when that file was processed; "EAF" is the
output_filename field - a filename PREFIX, not a full name; if two files
land on the same second within one run, a _2/_3/... suffix is appended so
neither output is overwritten). That object's content is a single
comma-separated, single-quoted line of the HICs of every eligible member
FROM THAT SOURCE FILE, e.g.:
    '1A2B3C4D5E6','9Z8Y7X6W5V4'
or, for a single eligible member:
    '1A2B3C4D5E6'
(an empty file if that source file had zero eligible members).
Source keyword files in error/ are not moved or deleted.

SUMMARY
-------
  no row in eam or facets                      -> flag_member_ineligible (auto, console message)
  any eligibility/date check fails (either row) -> flag_member_ineligible (auto, console message)
  all checks pass on both rows                  -> export_eligible_member_hic (auto, HIC written to
                                                     that source file's own EAF_<timestamp>.txt)

IMPLEMENTATION
--------------

HOW THIS RUNS
-------------
  1. Directly: `python -m jobs.process_eam_member_kwd_files`, or continuously
     via `--watch` (polls every SOP-owned bucket in the library on a timer).
  2. Via a ServiceNow incident: agents/job_remediation_agent.py keyword-matches
     this SOP from the ticket's text, the LLM picks one of this SOP's
     resolution_steps, and - if guardrails pass - common/remediation_executor.py
     runs the SAME deterministic job (not an LLM improvisation) via the
     export_eligible_member_hic / flag_member_ineligible handlers.

Not yet auto-triggered on S3 object-create - no event notification is
configured on the bucket.
